Every developer has committed the cardinal sin of secret sharing.

You needed to send a production database URL or a Stripe secret key to a teammate in a hurry. So you pasted it into Slack, sent it over Discord, or emailed a `.env` file. It took three seconds. It worked.

Six months later, that production secret is still sitting in plaintext inside searchable chat histories, export logs, third-party bots, and compromised laptop backups.

Most dedicated secret-sharing tools fail developers because they demand too much: either mandatory account creation, complex CLI configurations, or blind trust in a server database that actually has access to your plaintext.

**I built EnvDrop to solve both ends of the equation: absolute zero-knowledge cryptographic security with the frictionless UX of a 5-second pastebin.**

### Core Security Highlights

EnvDrop is engineered around a single invariant: **the server must remain completely blind.**

<Cards>
  <Card title="Client-Side Web Crypto">

Secrets are encrypted in-memory directly in your browser using the native Web Crypto API before a single byte leaves your machine.

  </Card>

  <Card title="URL Fragment Cryptography">

The decryption key lives strictly inside the URL hash fragment (#). By HTTP specification, browsers never send fragments to web servers.

  </Card>

  <Card title="Zero Signup Friction">

Paste a token or drop an entire .env file, click generate, and share. No accounts, no email verification, and no telemetry tracking.

  </Card>

  <Card title="Self-Destruct Mechanisms">

Configure drops to vaporize immediately after the first successful decryption, or enforce strict time-to-live (TTL) auto-expiry.

  </Card>

  <Card title="PBKDF2 Password Layer">

Add an optional recipient password. Uses PBKDF2 with high iterations to locally wrap the master key without transmitting the password.

  </Card>

  <Card title="Ephemeral Storage">

Backed by Upstash Redis with aggressive TTL evictions and per-IP rate limiting to defend against automated enumeration and brute-force attacks.

  </Card>
</Cards>

### The Zero-Knowledge Architecture 

How can a server store and serve an encrypted secret without having the ability to read it?

The magic lies in combining **AES-256-GCM** client-side encryption with standard web browser mechanics:

<Steps>
<Step>
**In-Memory Client Encryption**
    
    When you paste text or drop a `.env` file, your browser's Web Crypto subsystem generates an ephemeral 256-bit symmetric encryption key. It encrypts the payload using AES-256-GCM with a unique 12-byte initialization vector (IV).
</Step>

<Step>
**Server Stores Only Ciphertext Noise**
    
    The browser transmits *only* the encrypted ciphertext payload, IV, and expiry parameters to the server. The server stores this opaque binary blob in Upstash Redis. At no point does the encryption key touch the network request body or headers.
</Step>

<Step>
**The Key Lives in the URL Hash Fragment**
    
    The generated share link is formatted as `https://envdrop.dev/drop/<id>#<decryption-key>`. Under **RFC 3986**, anything following the `#` symbol is an internal browser anchor and is **never transmitted over HTTP/HTTPS**.
</Step>

<Step>
**Recipient Decrypts Locally**
    
    When the recipient opens the link, their browser fetches the encrypted blob by ID, reads the key from `window.location.hash`, and decrypts the secret in memory.
</Step>
</Steps>

```typescript
Sender's Browser                EnvDrop API / Redis              Recipient's Browser
       │                                  │                                  │
       ├─ Generate AES-256 Key            │                                  │
       ├─ Encrypt payload in-memory       │                                  │
       │                                  │                                  │
       ├─ POST encrypted blob ──────────► │                                  │
       │  (No key attached)               ├─ Store ciphertext with TTL       │
       │                                  │                                  │
       ├─ Receive Drop ID                 │                                  │
       ├─ Assemble link:                  │                                  │
       │  envdrop.dev/drop/ID#KEY         │                                  │
       │                                  │                                  │
       └─ Send link via your chat ─────────────────────────────────────────► │
                                          │                                  │
                                          │ ◄── GET /api/drop/ID ────────────┤
                                          │     (Server sees ID, not #KEY)   │
                                          ├─ Return ciphertext blob ────────►│
                                          │                                  │
                                          │    [Decrypt locally using #KEY]  │
                                          │    [Render plaintext in-memory]  │
                                          │                                  │
                                          │ ◄── DELETE /api/drop/ID ─────────┤
                                          ├─ Purge record (Burn on read)     │
```

### What You Can Do With It

<Tabs items={["Instant Secret Sharing","Full .env Drag-and-Drop","Password Shield (PBKDF2)"]}>
  <Tab value="Instant Secret Sharing">
  Paste raw API keys, private certificates, SSH credentials, or database connection strings.

  - **Burn After Read:** The secret is irrevocably purged from the database immediately after the recipient successfully decrypts it.
  - **Flexible Lifespans:** Select automatic expiration windows (10 minutes, 1 hour, 24 hours, or 3 days). If unread, it vanishes automatically.
  - **One-Click Clipboard:** Recipients can copy credentials cleanly with a single tap, with automatic clipboard clearing hints.
  </Tab>

  <Tab value="Full .env Drag-and-Drop">
  Sharing an entire environment configuration file shouldn't mean copying 40 separate lines.

  - **Drop Support:** Drag any `.env`, `.env.local`, or sensitive configuration file (up to 200KB) straight into the drop zone.
  - **Client-Side Syntax Parsing:** EnvDrop previews keys and values with syntax styling while keeping the file encrypted end-to-end.
  - **Direct Download:** The recipient can copy the file contents or download a cleanly formatted `.env` file directly to their project directory.
  </Tab>

  <Tab value="Password Shield (PBKDF2)">
  Need defense-in-depth in case someone intercepts the share link? Add an optional access password.

  - **Zero-Knowledge Password Verification:** The server never receives or stores your password.
  - **Key Wrapping:** The password is fed through **PBKDF2-HMAC-SHA256** with high iterations and a random salt to derive a key-encrypting key (KEK), which encrypts the master AES key.
  - **No Decryption Without Password:** Even with the full URL, the recipient must provide the password to unwrap the master key client-side.
  </Tab>
</Tabs>

### Engineering Deep Dive

<Callout type="info">
  **Engineered on `@redenv/e2ee`:** The cryptographic backbone powering EnvDrop is extracted into an independent, audited open-source library called <Link href="https://www.npmjs.com/package/@redenv/e2ee" target="_blank">**@redenv/e2ee**</Link>. It provides type-safe zero-knowledge encryption primitives for modern web and Node.js applications.
</Callout>

#### 1. Solving the Burn-After-Read Race Condition
A naive burn-after-read implementation destroys the secret the moment the GET request hits the server. But if the recipient's connection drops, their browser crashes, or an automated link preview bot (like Slackbot or Twitter preview crawler) fetches the URL, the secret is permanently lost before the human can read it.

EnvDrop prevents this with a **client-confirmed destruction protocol**:
1. The server delivers the encrypted ciphertext without purging it.
2. The client browser performs local decryption and verifies the integrity tag.
3. Only upon verified decryption does the client dispatch a signed, authenticated deletion signal back to the server to evict the key from Redis.

#### 2. Bot & Crawler Pre-Fetch Protection
Link unfurlers (Discord, Slack, iMessage) routinely ping URLs to generate link previews. EnvDrop server routes detect standard bot `User-Agent` headers and serve neutral OpenGraph metadata without ever touching the secret payload or burning TTL tokens.
